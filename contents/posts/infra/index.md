오늘 옆자리 팀원의 도움 요청. 모니터링 툴에서 이중화 서버중 한 서버인 2번째 WAS만 브로큰 파이프 에러가 터짐

저랑 다른 시스템을 운영하는 팀원이 한가지 요청을 했다. 최근에 인수인계 받은 시스템이 있는데, 모니터링 툴에서 배치를 진행하는 API에서 한쪽의 WAS만 Broken Pipe(ClientAbortException)이 일어나는 것. 팀원은 인프라 지식이 없어서 이중화 된 서버 중 한 쪽만 왜 이렇게 되는지 모르겠다고 한다. 그래서 짤막한 인프라 지식으로 해당 문제를 접근한 내용을 서술해보자 한다.

1번 WAS와 2번 WAS를 모니터링 하는 툴인 인터맥스를 확인해보니 1번 WAS에서는 600초가 넘는 배치 API도 에러 없이 잘 작동하고 있었다. 그러나 2번 WAS에서는 306초, 440초, 442초, 502초 등 대략적으로 300초가 넘어가는 API는 Broken Pipe 에러가 났다. 

Broken Pipe : 단순하게 클라이언트가 서버를 찔렀지만, 서버가 답을 원하는 시간에 안줘서 끊어버린 상태

당시 인프라가 어떻게 구성돼있는지는 모르겠지만, 여기서 바로 판단할 수 있는 것은 1번 WAS로 들어오는 것은 무언가의 타임아웃이 600초가 넘는 상황, 2번 WAS로 들어오는 무언가는 타임아웃이 300초로 설정된 것으로 판단하였다.

이후 어디서 끊었는지가 중요하기 때문에 인프라 구조가 어떤지부터 찾았다.

팀원은 EC2 두 개가 있는 것을 보여주었고, 레나 관리 페이지를 보여주었다. 레나 페이지에 들어가보니 WEB 서버가 2개, WAS가 2개가 보였다. 그러면 이 보다 위 계층 LB에서 각 WEB서버에 트래픽을 분산해주고 각 웹서버는 각 와스에게 트래픽을 주겠구나? 그러면 2번 웹서버가 2번 와스를 바라볼 때 커넥션 아웃이 생긴거 아닐까? 이게 아니면 그 위 L4 LB에서 끊긴걸까? 라고 판단하였다.

웹서버 설정 파일들을 보면서 판단한 내용 : 웹서버와 와스간에는 AJP 통신을 한다. 2번 웹서버의 http 타임아웃이 300초가 돼있었다. 

옳다쿠나! 2번 웹서버 http 타임아웃이 300초이기 때문에 브로큰 파이프 에러가 난거고, 그러면 1번 웹서버는 http 타임아웃이 엄청 크겠지? 라고 판단했다.

실상은 1번 웹서버도 http 타임아웃이 300초였다. 그리고 1번 웹서버와 2번 웹서버는 1번 와스와 2번 와스 모두 알고있었다. 즉, 1번 웹서버에 통신이 들어오면 1번 와스와 2번 와스 모두 랜덤으로 와스에게 트래픽 분산을 해주고, 2번 웹서버에 들어와도 동일하게 1, 2번 와스로 랜덤 분산한다.

대략적인 인프라 아키텍처 

```
                    [ 외부 클라이언트 (유저 / 타 시스템) ]
                                │
                                ▼
┌─────────────────────────────────────────────────────────────┐
│    1차 로드밸런서 (AWS ALB / NLB / L4 스위치)                    │
│    • EC2 #1과 EC2 #2로 트래픽을 분산 (Random / Round-Robin)     │
└─────────────────────────────────────────────────────────────┘
                                │
        ┌───────────────────────┴───────────────────────┐
        ▼                                               ▼
┌───────────────────────────────┐ ┌───────────────────────────────┐
│          EC2 #1 노드          │ │          EC2 #2 노드            │
│                               │ │                               │
│      ┌─────────────────┐      │ │      ┌─────────────────┐      │
│      │   WEB 1 서버     │      │ │      │   WEB 2 서버     │      │
│      └─┬─────────────┬─┘      │ │      └─┬─────────────┬─┘      │
│        │             │        │ │        │             │        │
│AJP (1) │     AJP (2) │        │ │        │ AJP (3)     │ AJP (4)│
│(Local) │     (Cross) │        │ │        │ (Cross)     │ (Local)│
│        │             │        │ │        │             │        │
│        ▼             └────────┼─┼────────┼──────┐      ▼        │
│   ┌─────────┐                 │ │        │    ┌─┴─────────┐     │
│   │  WAS 1  │ ◄───────────────┼─┼────────┘    │  WAS 2    │     │
│   │ (Tomcat)│                 │ │             │ (Tomcat)  │     │
│   └─────────┘                 │ │             └───────────┘     │
│                               │ │                               │
│      * RENA Manager/Agent     │ │      * RENA Manager/Agent     │
└───────────────────────────────┘ └───────────────────────────────┘
```

이때부터 머리가 아파졌다. 웹서버에서 와스 둘에게 랜덤으로 트래픽을 분산하는데 타임아웃이 서로 다르게 걸 수 있다? 처음 듣는 내용이라 AI와 친하게 지내본 결과 레나 웹서버는 아파치 웹서버 기반이고 mod_jk 플러그인 모듈에서 로드밸런서 worker 내용이 들어있다고 한다.

```toml
# 1. 외부(Apache)에 공개할 대표 Worker 이름 지정
worker.list=lb_was

# 2. [반장 일꾼] 로드밸런서 타입 선언 및 하위 일꾼 지정
worker.lb_was.type=lb
worker.lb_was.balance_workers=was1, was2   # "나는 was1과 was2에게 일을 나눠줄 거야!"

# 3. [실제 작업 일꾼 1] WAS 1 정보 및 타임아웃
worker.was1.type=ajp13
worker.was1.host=127.0.0.1
worker.was1.port=8009
worker.was1.reply_timeout=60000

# 4. [실제 작업 일꾼 2] WAS 2 정보 및 타임아웃
worker.was2.type=ajp13
worker.was2.host=10.0.2.20
worker.was2.port=8009
worker.was2.reply_timeout=600000
```

위 같이 1번 와스와 2번 와스의 커넥터 타임아웃을 다르게 설정할 수 있다고 한다.

그래서 해당 파일을 열어본 결과... 타임아웃 내용이 없었다...

머리가 뜨거워졌다. 대체 무엇이... 나는 무엇인가 나는 누구인가 나는 뭘 보고 있는건가... 아무리 이해가 안돼길래 혼자만의 생각에 빠져 경우의 수를 따져봤다. 현재 타임아웃 관련된 건 L4에서의 타임아웃, 웹서버의 HTTP 타임아웃, 웹서버 로드밸런서 역할을 하는 worker의 AJP 타임아웃, WAS의 커넥터 타임아웃 총 4가지이다. L4는 내가 설정할 수 없고, 만약 설정돼있어도 2번 WAS만 되는 것은 이상한 모습이라 판단. HTTP 타임아웃은 '둘 다' 300초. WAS의 커넥터 타임아웃도 '둘 다' 300초

음... 사실 타임아웃 설정이 웹서버와 와스에 안돼있는 거 아닐까? 재시작 하면 되지 않을까? 최근에 PM작업을 했기 때문에 아니라고 한다. 그럼 대체 왜... 고민하던 차 전임자와 개발자 형님들에게 연락하여 자문을 구해봤다. 그 배치는 젠킨스에서 시스템에 있는 API를 호출하고 해당 API는 타 ERP에 인터페이스를 하는 거다. 브로큰 파이프 나도 실제로 와스에선 배치는 정상적으로 데이터는 받는다. 등등 내용을 듣고 생각을 하였다. 

배치라 해서 우리쪽에서 스케줄링을 돌려 타 시스템과 인터페이스를 하는건 줄 알았다. 그러나 타 시스템(젠킨스)이 우리쪽 API를 찌르고 타 시스템을 찌르는 거다. 이거보고 어? 브로큰 파이프가 터지는 순간이 언제지? 젠킨스쪽에는 어떤 내용이 있지 않을까 하고 바로 젠킨스 스케줄링을 들어가서 로그를 살펴봤다. 

어? 젠킨스에선 1번 와스 2번와스 상관없이 둘다 502 BAD Gateway, Server Connect 어쩌고 저쩌고... 어!!!! 이거다. http 타임아웃이 300초로 잡혀있었으니까 둘 다 브로큰 파이프 에러가 떨어지는 것이 맞았다. 근데 어떤 이유로 인해 모니터링 툴에서 1번 와스만 에러가 안떨어지는 것으로 판단했다. 그러면 무엇이냐? 모니터링 툴에서 1번 와스에만 예외처리를 하고 있는게 아닌가 하고 바로 인터맥스 설정 파일 위치를 AI에게 물어본다음에 1번 와스와 2번 와스 모두 키고 인터맥스 설정 파일을 찾아 서로 비교를 했다.

그리고 1번 와스에 인터맥스 설정 파일에만 써있는 `EXCLUDED_EXCEPTION : ClientAbortException`

보고나서 바로 마음속으로 찾았다를 외치며 팀원에게 설명하였다.

1, 2번 와스 둘 다 브로큰 파이프가 터진 것은 맞다. 간략하게 아래 내용에서 스프링부트가 타시스템 데이터를 받아서 가공하고 웹서버 쪽으로 응답을 보내려다가 HTTP 통신이 끊겨있어 Broken Pipe에러가 터진것이고, 젠킨스는 웹서버로부터 서버가 응답이 없다는 내용으로 502를 받았다. 그렇기 때문에 WAS는 데이터 처리는 문제없이 했던 것이다.

```
Jenkins
   │
   │ HTTP 요청
   ▼
1차 LB
   ▼
WEB
   │
   │ AJP
   ▼
Spring Boot (embedded Tomcat)
   │
   │ 타 시스템 호출
   ▼
처리 완료
   │
   │ HTTP Response 작성
   ▼
Spring Boot의 Tomcat Connector
   │
   │ AJP
   X  이미 연결이 끊어짐
   │
   └── Broken pipe
       ↓
   WEB / LB 쪽에서는
   upstream 응답을 정상적으로 못 받아
   502 반환
       ↓
     Jenkins
```



그래서 팀원에게 1번 2번 와스 둘 다 Broken Pipe 에러가 난 것이 맞고, 하필 모니터링 툴에서 1번 와스만 해당 익셉션이 예외처리 되어있던 거다. 그래서 2번 WAS에서만 익셉션이 보인거고, 젠킨스는 둘 다 502가 뜬 것이다. 우선 브로큰 파이프가 뜨기 때문에 웹서버의 HTTP 타임아웃, 웹서버 로드밸런서 역할을 하는 worker의 AJP 타임아웃, WAS의 커넥터 타임아웃을 최소 600초로 올려야하고, 600초가 넘는 배치가 있다면 타임아웃을 늘릴 것. 그리고 모니터링 툴 설정을 1번 와스와 2번 와스 동일하게 맞출 것.



결론

이걸 하면서 레나가 어떻게 구성되어서 쓰이는지 자세히 알게 되었고, 배치라고해서 이럴꺼라 짐작하고 시작하지말고 처음 단계부터 차근차근 보는 것을 명심하겠다고 생각했다. 처음부터 젠킨스 배치임을 알고 젠킨스를 봤으면 더 빨리 끝나지 않았을까 한다...
